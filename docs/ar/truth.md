# АР-реестр · Источники истины и изоляция

> Блок ведения: **Источники истины и изоляция**. Владелец: архитектура ядра. Диапазоны номеров: `1-4,6-7,34,44-48,66,78,83,98-99`.
> Нумерация сквозная по всей системе — см. [AR-PROTOCOL.md](../method/AR-PROTOCOL.md).
> Индекс всех реестров: [INDEX.md](./INDEX.md). Ворота: [G-CHECKS.md](../G-CHECKS.md). Линзы: [LENSES.md](../method/LENSES.md).

| № | Решение | Статус | Ворота | Линзы |
|---|---|---|---|---|
| AR-1 | Identity, организации, роли верхнего уровня, устройства — **Флёрус** (OIDC, BFF-модель по ADR-0005). EduStore — relying party, свой auth не строит; `sub` = `User.id`. | [заменено AR-46] | G-18 | L-1, L-6 |
| AR-2 | Единица изоляции тенанта = **школа = `Workspace`** (`florusWorkspaceId` из claim), ключ `workspaceId` на каждой доменной таблице (57 моделей в `tenant-models.ts`). `Organization` — синглтон платформы, доменные данные на неё не ключуются. | [РЕШЕНО] | G-1 | L-7, L-1 |
| AR-3 | Ребро `parenthood` (родитель↔ребёнок) — **зеркало директории Флёруса**; единственный писатель — `ParenthoodSync`, домены только читают. EduStore рёбра не авторит. | [заменено AR-48] | G-2 | L-1, L-13 |
| AR-4 | **Канон оценок — `JournalCell`**, `Grade` мигрируется и удаляется (решение владельца 2026-07-28). `JournalCell` расширяется полями `source`/`comment`; чтение метрик/отчётов/голоса переводится на `JournalCell`; данные переносятся миграцией; единственный писатель — `grade.posted`. Ворота — G-12. | [заменено AR-83] | G-12 | L-1, L-9 |
| AR-6 | Журнал EduStore **не является системой записи для госшкол** (273-ФЗ ст.16 ч.3.1, ADR-0002): частные школы — полный журнал; госшколы — рабочий слой + синк-коннектор в гос-ГИС (слот, не реализован). `Workspace.sector` заведён, ветвление пока не читается. | [РЕШЕНО, слот] | нет: слот (синк-коннектор гос-ГИС) | L-13, L-6 |
| AR-7 | Права — **данные в БД** (`Permission`/`RolePackage`), каталог версионируется в коде (`catalog.ts`, 35 прав, 6 пакетов) и идемпотентно синкается на буте. Отдельный policy-сервис (OPA/Cerbos) не вводится. | [РЕШЕНО] | G-10 | L-8 |
| AR-34 | **Tenant fail-closed** (решение владельца 2026-07-28): аутентифицированный пользователь без workspace получает `{tenantId:null, system:false}` → tenant-guard бросает 403 на любой guarded-модели. Кейсы «до выбора школы» (`/me`, provision) — только через явный `runAsSystem` в конкретных сервисах. Owner-кейс не контраргумент: owner — tenancy-роль, панель — Флёр (AR-16). Ворота — G-11. | [РЕШЕНО] | G-11 | L-7 |
| AR-44 | **Иерархия тенантов: `workspace` → `worknet` → `federation`** (продуктовая логика §2). Единица изоляции данных — по-прежнему **workspace = школа** (уточняет AR-2); `worknet` — биллинг-сущность верхнего уровня и **атрибут** школы (`Workspace.worknetId` уже в схеме), а не второй ключ изоляции: вторая граница — это второе место, где можно ошибиться. Агрегация по сети строится явным перечислением школ, а не ослаблением tenant-guard. `federation` — слот, не проектируется. | [РЕШЕНО] | G-22 | L-7, L-1 |
| AR-45 | **Контингент — сервис-владелец данных** об учениках, классах и зачислениях (продуктовая логика §3). Журнал, дневник, расписание, питание читают его только через контракт (API или события); прямой SQL-доступ к таблицам контингента запрещён. Защищает от рассинхрона уже внутри Schoolium и даёт единый контракт для будущих сервисов EduStore без переписывания под каждую школу. | [РЕШЕНО] | G-23 | L-1, L-5 |
| AR-46 | **Идентичность пользователя — номер телефона**; доменная модель пользователя отделена от способа входа, поэтому переход на единый аккаунт EduStore меняет слой авторизации, а не модель пользователя. Заменяет внешний IdP как источник идентичности (AR-1). | [РЕШЕНО] | G-24 | L-1, L-6 |
| AR-47 | **Область уникальности телефона — вся инсталляция**: `User` глобален, принадлежность школе — через `Membership`; требование «в одной школе телефон встречается один раз» выполняется автоматически. Альтернатива (пользователь на workspace) потребовала бы слияния записей при появлении единого аккаунта — ровно той миграции модели пользователя, которой решение избегает. Цена названа: глобальная уникальность — канал утечки факта существования пользователя между школами, закрывается сценарием входа (регистрация не сообщает о записи в другой школе, присоединение — по приглашению). **Подтверждено владельцем 2026-08-20.** | [РЕШЕНО] | G-24 | L-1, L-7 |
| AR-48 | **Ребро `parenthood` авторится внутри Schoolium**; единственный писатель — модуль контингента: школа создаёт ребро при зачислении, родитель подтверждает при входе. Заменяет зеркалирование директории внешнего IdP (AR-3). Инвариант миноров (приватный DM взрослый↔минор только по ребру) сохраняется и переносится на новый источник ребра. | [РЕШЕНО] | G-25 | L-13, L-1 |
| AR-66 | **Регистрация и присоединение ко второй школе — независимые операции**, выполняются параллельно и не конфликтуют: `User` глобален (AR-47), членство в школе — отдельная запись, гонки за один ресурс нет. Подтверждено владельцем 2026-08-20. | [РЕШЕНО] | G-24 | L-4, L-7 |
| AR-78 | **Ученик с отметками не удаляется — деактивируется**: строки журнала и история сохраняются, деактивированный исключается из новых колонок и пересортировки; физическое удаление доступно только для записи без отметок (опечатка при вводе). Пол и ФИ — обязательные поля записи контингента, отчество — опциональное. | [РЕШЕНО] | G-35 | L-1, L-9 |
| AR-83 | **Канон отметок 1.1.1 — модель `Mark`**, единственный писатель — модуль журнала (`journal.mark.posted.v1`). Прежний канон `JournalCell` (AR-4) остаётся внутри контура КТП-движка, который в объём 1.1.1 не входит: два хранилища живут в одной базе, но не в одном сценарии, и ворота G-12 продолжают стеречь старый контур до его вывода. План вывода — вместе с движком КТП/КПП, отдельным инкрементом с миграцией данных; до тех пор запрет прямой: журнал 1.1.1 не читает и не пишет `JournalCell`, движок не читает и не пишет `Mark`. | [РЕШЕНО] | G-35 | L-1, L-9 |
| AR-98 | **Пилот — одна школа, но тенант настоящий, а не подразумеваемый**: bootstrap (AR-93) создаёт реальный `Workspace`, и каждый пользователь входит в систему только через членство в нём — QR модератора создаёт `Membership(userId, workspaceId, roles)`, других путей появления пользователя нет. Запрещено: константа «школы по умолчанию» в коде, чтение «первой школы из таблицы», запись без `workspaceId`. Пользователь без членства не видит ничего (fail-closed AR-34). Так Schoolium не вырождается в «одна школа = вся ERP»: вторая школа — это второй bootstrap без единой правки кода, и G-1 обязана оставаться зелёной при двух workspace в одной базе. | [РЕШЕНО] | G-1, G-11 | L-7, L-1 |
| AR-99 | **Таблицы контура доступа названы поимённо и разведены с доменными**: домен 1.1.1 — 11 моделей (`SchoolClass`…`LessonTopic`), контур доступа — восемь: `User`, `Membership`, `Workspace` (переиспользуются существующие, чистка `florus*`-полей — отдельный инкремент AR-58) плюс **новые** `AppSession`, `DeviceLinkToken`, `LoginCode`, `ActivationToken`, `BootstrapLink`. Legacy `Session` (OIDC-поля `accessToken`/`refreshToken`/`florusSid`) не расширяется и не переиспользуется — она принадлежит вытесненному контуру (AR-46, AR-49) и уходит вместе с ним; прецедент тот же, что у AR-83 и AR-84. **Правило изоляции:** `User`/`Membership` вне tenant-guard осознанно (членства человека живут в разных школах), `AppSession` несёт `workspaceId` активного тенанта, `LoginCode`/`ActivationToken` — под tenant-guard, `DeviceLinkToken` до подтверждения анонимен и получает `workspaceId` в момент привязки. **Состояние привязки устройства живёт в БД, а не в памяти процесса** — рестарт API не рвёт открытые QR (дыра существующего device-flow). | [РЕШЕНО] | G-1, G-44 | L-1, L-7 |

# AUTH_FLOW — регистрация, вход, подключение к школе (v2)

Статус: **ЗАФИКСИРОВАН** (2026-07-09). Все решения — по AR-реестру (AR-1…AR-29);
здесь только сборка flow, номера AR — ссылки. Открытые узлы не блокируют заморозку (§9).
Читатель: агент/разработчик. Связанные: `AR_REGISTER.md`, `TENANCY.md`, `PARAMETERS.md`, `kernel/authz`, `kernel/entitlements`, `adr/` (ADR-0005 — пересмотреть по AR-1).

## 1. Основания

Флёр опционален, EduStore самостоятелен и является источником истины (AR-1, AR-2). User платформенный, Membership = user×workspace (AR-3). Роли = пакеты разрешений, таблицы прав (AR-8). Клиенты: desktop (Tauri+SQLite), web, mobile; скачивание с сайта, сессия только через аккаунт.

## 2. Роли flow

| Роль | Действие |
|---|---|
| Админ школы (CRM) | «Пользователи» → «Подключить коллегу» |
| Админ сети устройств (IT) | Сессии/устройства, восстановление доступа (M6). Отдельная сущность в правах, на старте совмещён (AR-29) |
| Сотрудник | Регистрация, скан QR/код, работа в 1..N школах |
| Главная школа worknet | Покупка сервисов на сеть (AR-28) |

## 3. Сеть маршрутов

| # | Маршрут | Итог |
|---|---|---|
| M1 | Регистрация: телефон+ФИО+пол+ДР+@handle, верификация звонком SMSAero (AR-4, AR-5) | аккаунт |
| M2 | Подключение к школе: QR с экрана админа (AR-9…AR-11, AR-13) | membership |
| M3 | Код-fallback десктопа, равноправен QR (AR-12, узел: handoff) | membership |
| M4 | Флёр SSO → merge по номеру (AR-7) | сессия |
| M5 | Восстановление сессии: cookie 10 лет (AR-14) | сессия |
| M6 | Восстановление доступа через админа сети устройств (AR-19…AR-22) | сессия+устройство |

Каждый маршрут заканчивается в одном состоянии: активная сессия (+ активная membership для работы в школе).

## 4. M1 — регистрация

1. Телефон + ФИО + пол + ДР (flow как у Google).
2. Верификация — звонок, SMSAero [внешний контракт].
3. @handle: глобально уникален, регистронезависим, смена ограничена, резерв-имена (AR-5 [дефолт]).
4. Аккаунт без membership → статус-экран «вы гражданин EduStore; для работы в школе попросите админа показать QR» — не тупик.

QR не создаёт аккаунт: нет аккаунта → QR ведёт в M1, затем привязка тем же токеном (AR-9).

## 5. M2/M3 — подключение к школе

1. Админ выбирает роль (пакет прав) ДО генерации → экран: QR + код (AR-10).
2. Токен: одноразовый, TTL 5 мин [дефолт], скан только напрямую с экрана админа; результат («подключился @handle, ФИО») виден админу (AR-10).
3. Скриншот: FLAG_SECURE на mobile; web/desktop best-effort, гарантия — одноразовость+TTL+видимый результат (AR-11).
4. Повторный скан членом — идемпотентен (AR-13).
5. Десктоп: ноутбук запрашивает код → вводится код с экрана админа. Пошаговый handoff: МФ собирают, сверка с `domains/oidc-device` (AR-12 [узел]).

## 6. Сессии и сеть устройств

- Хаб аккаунта «Сессии на устройствах»: название, тип (mobile/web/desktop), организация/сервис (AR-14).
- Видимость сессий — разрешение: дефолтный скоуп workspace; worknet — грант главной школы; сессия помечена организацией, личные видны только владельцу (AR-19).
- Режим устройства «личное»/«общее» — явный маркер при первом входе, виден админу сети устройств (AR-15). Общее: экран выбора карточек профилей при закрытии/выходе.
- Локальный замок (PIN/биометрия) — дефолт для персонала на любом устройстве (AR-16).
- Доверенные устройства: помечает владелец из хаба, вход без доп. верификации; список пропускаемых проверок [узел] (AR-17).
- «Завершить сессию» удалённо: владелец и админ сети устройств (AR-20). Автозавершение при неактивности > 12 мес [дефолт] (AR-18).

### FSM: сессия устройства

| Состояние | Событие → переход | Дом-экран | Терминал? |
|---|---|---|---|
| S0 пустое устройство | вход/регистрация → S1 | first-run: вход/регистрация | нет |
| S1 активная (профиль X) | закрытие/выход на общем → S2; блокировка замка → S3; отзыв прав (event) → S4 | кабинет | нет |
| S2 выбор профиля | профиль без замка → S1; с замком → S3; добавить профиль → S0-подпоток | карточки профилей | нет |
| S3 замок (PIN/пароль/био) | верный → S1; неверный → S3 + диагностируемая ошибка; отмена → S2 | ввод | нет |
| S4 доступ отозван | новое приглашение/реавторизация → S1 | статус «доступ отозван» + причина | нет |

Полнота: у каждого состояния выход и дом; терминалов нет (цикл устройства).

### FSM: Membership

| Состояние | Событие → переход | Дом | Терминал? |
|---|---|---|---|
| отсутствует | валидный токен приглашения → активна | «попросите QR у админа» | нет |
| активна | отзыв (увольнение) → отозвана | кабинет школы | нет |
| отозвана | новое приглашение → активна | статус-экран | да (до нового приглашения) |

## 7. Отзыв прав и офлайн

- Отзыв — мгновенный event-cascade: страница закрывается сразу; push-канал WS/SSE [узел: контракт]; аккаунт не удаляется (AR-23).
- Регистрация/подключение — online-only; офлайн: локальная работа (записи сразу в локальную БД) + восстановление сессии (AR-24).
- Локальные данные: шифрование at rest; ключ ре-выдаётся при коннекте, TTL 7 дней [дефолт]; отзыв → wipe своего каталога (online — event, offline — при синке); вечный офлайн → ключ протухает (AR-25). Чужие файлы на диске не трогаются; скачанное — за периметром, контроль разрешением «может скачивать» per-документ (AR-26).
- Синк с отозванного аккаунта — fail-closed целиком, данные школы не меняются; легитимные офлайн-правки до отзыва вносит админ вручную (AR-27).
- Конфликты синка данных — вне дока [слот: SYNC.md].

### 7а. M6 — восстановление доступа

1. Админ сети устройств → устройство пользователя → QR подсоединения (видимость по скоупу AR-19: чужие сессии не раскрываются).
2. Пользователь сканирует новым устройством → вход.
3. Развилка одним тапом: «старое со мной / в ремонте → оставить сессию» | «утеряно → завершить сессию» (AR-21).
4. Смена номера — явный шаг + ре-верификация звонком на новый номер (AR-22).

# Дорожная карта проработки архитектуры v2 (без имплементации)

> Дата: 2026-07-08. Формат работы по зонам — как в домене auth:
> **AR-реестр** (сквозная нумерация, следующий домен начинает с AR-30) +
> **FSM-таблицы** (по образцу AUTH_FLOW §6: состояние/событие/дом/терминал) +
> при необходимости мини-ADR. Зона закрыта = реестр зафиксирован, узлы
> помечены и не блокируют.
>
> Домен «идентичность/вход/устройства» — ✅ зафиксирован (AR-1…AR-29).
> Его открытые узлы распределены по зонам ниже (указано где).

## Критический путь (последовательно — каждая блокирует следующую)

### Z1. Тенантность и оргструктура — НАЧАТЬ ЗДЕСЬ
Почему первая: AR-1 выбил из-под tenancy источник истины (claim Флёра);
пока не решено «как рождается школа», нельзя финализировать ни права,
ни схему, ни онбординг.

Решить:
- Жизненный цикл Workspace без Флёра: кто и как создаёт школу (self-serve
  регистрация школы? продажа → провижининг оператором?); кто становится
  первым админом; FSM школы (создана→активна→приостановлена→архив).
- Worknet: «главная школа» (AR-19/AR-28 на неё ссылаются, в модели её нет),
  как школа входит/выходит из сети, права главной над сетью.
- Организация-платформа: остаётся ли трёхуровневая модель
  Organization(платформа)→Worknet→Workspace или упрощается.
- Механизм изоляции в коде: RLS vs Prisma `$extends` (v1: deprecated `$use`);
  `Workspace.sector` (гос/частный, 152-ФЗ §6.5) — читается ли ветвлением.
- Редакция TENANCY.md + ADR-0006 (self-sovereign identity, вытеснение ADR-0005).

Опора: `TENANCY.md`, tenant-кластер схемы, `kernel/tenant`, AUTH_CHECK §A1/A11.
Артефакт: AR-30+ «оргструктура», FSM школы, правленый TENANCY.md.

### Z2. Каталог прав (таблицы разрешений)
Почему вторая: AR-8 объявил «роль = пакет прав», но сам каталог — объекты ×
действия × скоупы — не собран; он нужен и движку (кто утверждает КТП),
и UI (что показывать), и сессиям (видимость по AR-19).

Решить:
- Полная матрица: разделы → экраны → действия (расширение `catalog.ts` §5.1)
  для ВСЕХ кабинетов, включая новые пакеты: CRM-админ, админ сети устройств
  (AR-29), owner.
- Совмещение пакетов: правило union, конфликты (deny-переопределения нужны?),
  скоупы разрешений (workspace / worknet / объект / личное).
- Разграничение чувствительного: учитель не видит risk-score (канон AUDIT.md),
  психолог-доступы, «может скачивать» per-документ (AR-26).
- Кто раздаёт пакеты: админ школы назначает sub-роли (бывш. staff-маппинг).
- Узел AR-6 (сертифицированные аккаунты) — сюда: класс аккаунта как атрибут прав.

Опора: `kernel/authz/catalog.ts`, ENGINE.md §RBAC, AUTH_CHECK §A3/A12.
Артефакт: AR-«права» + канонические таблицы прав (та самая заморозка) +
таблица пакетов по кабинетам.

### Z3. Образовательный движок и единая доменная модель
Почему третья: ядро продукта; требует Z2 (кто что утверждает). Здесь же
закрывается двоевластие Phase-0/Phase-1.

Решить:
- Канон: журнал = JournalCell/grade.posted, урок = Lesson FSM (подтвердить
  формально, зафиксировать что Grade/planning-модели v1 не существуют в v2).
- Домоделировать Json-контракты: AssessmentPolicy (items/coefficients/scale),
  OrgStandards (спарки/физминутки/порядок — применение в Solver),
  TimingProfile→Lesson FSM, BriefTest.itemMatrix.
- Стабы движка из ENGINE.md: реальный календарь дат (слот→дата по неделям
  вместо TERM_START+seq), затухание ИОМ (per-signal timestamps),
  индивидуальная экспозиция тем.
- FSM-таблицы по образцу AUTH_FLOW: урок, КТП, КПП, летучка, IOM-сигналы.
- Границы ИИ: ai-query (id↔code граница №2), что остаётся 0-ИИ.
- Расписание (Timetable): кто строит, санпин-констрейнты — глубина v2.

Опора: `domains/engine` + `ENGINE.md` (лучшая база из всех зон),
`domains/standards`, REWRITE_AUDIT §4.
Артефакт: AR-«движок», FSM-пакет, событийный контракт `edu.*` v2.

## Сквозные зоны (параллельно с критическим путём)

### Z4. Событийный канон + realtime + офлайн-синк
Решить:
- Канон конверта/нейминга `<param>.<aggregate>.<verbPast>.v1` — подтвердить
  из PARAMETERS.md §3 как закон v2; реестр событий по доменам (кто emits,
  кто consumes, толстые/тонкие для ПДн).
- Узел AR-23: контракт realtime-канала (WS vs SSE, auth канала, что несёт:
  только «инвалидация» или данные), деградация при офлайне.
- SYNC.md: конфликты офлайн-правок Tauri (fail-closed по AR-27 — что дальше),
  что синкается вообще (какие домены офлайн-writable).
- Транспорт продакшена: когда in-process шины хватит перестанет (NATS-триггер).

Опора: PARAMETERS.md (канон готов на 80%), kernel/outbox, AUTH_CHECK §A8/A10.
Артефакт: AR-«события» + реестр событий + контракт канала + SYNC.md.

### Z5. Клиентская стратегия и каркас UI
Решить:
- Матрица клиентов: Tauri desktop / web / mobile — кто из них какой кабинет
  несёт, судьба PWA-офлайна (рекомендация AUTH_CHECK §A10: web тонкий,
  офлайн = desktop).
- Один реестр вместо трёх: обобщённый SectionDescriptor (зоны как данные)
  на все кабинеты; роутер; одна ДС (база admin/ds) + токены/prefs.
- Генерация shared-контракта из схемы (Prisma→zod) — правило №4 README.
- Голос: место в UI v2 (десктоп-микрофон? mobile-first?), деградация.

Опора: v2/web, ADR-0003, аудит фронта в REWRITE_AUDIT.
Артефакт: AR-«клиенты» + ADR по стеку клиентов. После заморозки Z1-Z3+Z5 —
детальное описание требуемого UI по кабинетам (проход /uix-master).

## Сборочные зоны (после заморозки критического пути)

### Z6. Схема данных v2 (компилируется из Z1-Z5)
Дельта уже известная (AUTH_CHECK §D4): User(+phone/handle/пол/ДР),
Membership(+status+N:M пакеты), Session(+хаб), UserDevice, Worknet(+main),
Entitlement(+scope), InviteToken. Плюс: ID-политика (cuid подтвердить),
enum'ы вместо строк-статусов, пер-домен группировка, что НЕ переносится.
Артефакт: schema.prisma v2 (draft) + ERD по кластерам.

### Z7. Комплаенс 152-ФЗ (сквозная ревизия)
Consent-цели v2, audit-реестр (развязать от доменных импортов — вердикт
аудита), ПДн в событиях (тонкие для спецкатегорий), данные миноров
(инварианты comm — уже канон), deletion/обезличивание, сектор.
Опора: consent/audit (as-is), PARAMETERS.md §6. Артефакт: AR-«ПДн».

### Z8. Биллинг и дистрибуция
AR-28 доразвернуть: структура SKU v2, trial, worknet-закупки, промо;
скачивание desktop-клиента «с сайта, сессия через аккаунт» (AUTH_FLOW §1).
Опора: kernel/entitlements, skus.ts. Артефакт: AR-«биллинг» + спека
entitlements (слот из AUTH_FLOW §8а).

### Z9. Инфра и качество
CI с зубами (lint/typecheck/тесты/миграции), тестовая стратегия
(инварианты → тесты: tenant fail-closed, inbox, depth-guard, движок,
auth-FSM), наблюдаемость (трейсинг каскадов по correlationId), бэкапы,
деплой v2 (single-VPS остаётся?). Артефакт: AR-«инфра» + ci.yml v2.

## Порядок и загрузка

```
Неделя-такт 1: Z1 (тенантность) ─┐
Неделя-такт 2: Z2 (права)        ├─ критический путь, последовательно
Неделя-такт 3: Z3 (движок)      ─┘
параллельно:   Z4 (события/sync), Z5 (клиенты) — можно вперемешку с Z1-Z3
после:         Z6 (схема) → Z7-Z9 (пакетом) → UI-проход по кабинетам → сборка
```

Правило такта: зона закрывается фиксацией реестра (как AR-1…29), открытые
узлы получают номер и владельца, не блокируют следующую зону. Каждая зона
начинается со сверки с кодом (как AUTH_CHECK) — противоречия наружу до
заморозки, а не после.

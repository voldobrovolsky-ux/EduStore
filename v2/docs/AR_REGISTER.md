# AR-реестр EduStore — домен «идентичность, вход, устройства»

Первый реестр проекта, нумерация сквозная (следующие домены продолжают с AR-30).
Статусы: [РЕШЕНО] — зафиксировано · [дефолт] — разумное умолчание, можно изменить · [узел] — требует внешней информации/решения.
Дата фиксации: 2026-07-09. Экосистемное следствие: ADR-0005 (BFF-OIDC как единственный вход) пересмотреть — вытеснен AR-1.

## Источники истины и идентичность

| № | Решение | Статус |
|---|---|---|
| AR-1 | EduStore самостоятелен: сам выпускает токены сессии и хранит пользователей; Флёр — опциональный SSO, не зависимость. Почему: независимый вывод продукта, Флёр вторичен. | [РЕШЕНО] |
| AR-2 | Источник истины — EduStore; токены API и контракты интеграциям выдаёт он, а не принимает (исключения — per-контракт по сложности). | [РЕШЕНО] |
| AR-3 | User — платформенный («гражданин»), может существовать без школ (методист); связь со школой — Membership (user×workspace). Две соло-школы через общего сотрудника в сеть не объединяются. | [РЕШЕНО] |
| AR-4 | Регистрация: телефон + ФИО + пол + дата рождения + @handle; верификация номера телефонным звонком через SMSAero (SMS дорого). | [РЕШЕНО] |
| AR-5 | @handle глобально уникален, регистронезависим, смена ограничена периодом, есть резерв-список имён — идентификатор тегирования в экосистеме. | [дефолт] |
| AR-6 | Сертифицированные (верифицированные организацией) аккаунты существуют как класс; механизм сертификации не спроектирован. | [узел] |
| AR-7 | Вход через Флёр при уже зарегистрированном номере → merge аккаунтов; правила конфликтов merge (расхождение ФИО и т.п.) не определены. | [РЕШЕНО]+[узел] |
| AR-8 | Ролей как фиксированных сущностей нет: роль = пакет разрешений/ограничений; права — таблицы разрешений на объекты; роли совмещаемы. База — kernel/authz (CONCEPT). | [РЕШЕНО] |

## Подключение к workspace

| № | Решение | Статус |
|---|---|---|
| AR-9 | QR не создаёт аккаунт — только привязывает membership к существующему; нет аккаунта → QR ведёт в регистрацию, затем привязка тем же токеном. Почему: исключает дубли идентичностей. | [РЕШЕНО] |
| AR-10 | Токен приглашения: одноразовый, TTL 5 мин [дефолт], роль (пакет прав) выбирается админом ДО генерации, скан только напрямую с экрана админа, результат скана виден админу. | [РЕШЕНО] |
| AR-11 | Защита QR от скриншота — best-effort (FLAG_SECURE на mobile; web/desktop технически не блокируются); гарантия — одноразовость+TTL+видимый результат, не DRM. | [РЕШЕНО] |
| AR-12 | Код-fallback для десктопа равноправен QR; пошаговый handoff собирают МФ, владелец сверяет с domains/oidc-device (RFC 8628). | [узел] |
| AR-13 | Повторный скан уже-членом той же школы — идемпотентен («вы уже в школе N»). | [РЕШЕНО] |

## Сессии и сеть устройств

| № | Решение | Статус |
|---|---|---|
| AR-14 | Long-term cookie 10 лет; хаб аккаунта «Сессии на устройствах» = сеть устройств пользователя (название, тип mobile/web/desktop, организация или сервис). | [РЕШЕНО] |
| AR-15 | Режим устройства «личное»/«общее» — явный маркер при первом входе, регистрируется в сети устройств, виден админу сети устройств; на общем — экран выбора карточек профилей. | [РЕШЕНО] |
| AR-16 | Локальный замок приложения (PIN/биометрия) — дефолт для ролей персонала на ЛЮБОМ устройстве. Почему: теряются личные устройства; кука живёт 10 лет — экран заперт (стандарт банковских приложений). | [РЕШЕНО] |
| AR-17 | Доверенные устройства помечает владелец из хаба; вход с них без доп. верификации; полный список пропускаемых проверок — перечислить. | [дефолт]+[узел] |
| AR-18 | Автозавершение сессий без активности > 12 месяцев (гигиена: мёртвые сессии = поверхность атаки). | [дефолт] |
| AR-19 | Видимость сессий = разрешение в таблицах прав: скоуп по умолчанию — workspace; worknet-скоуп — отдельный грант главной школы (симметрично AR-28). Каждая сессия помечена организацией; админ видит только сессии своего скоупа; личные сессии (без организации) видны только владельцу. | [РЕШЕНО] |
| AR-20 | «Завершить сессию» удалённо — доступно владельцу (хаб) и админу сети устройств; существует всегда, не форсируется. | [РЕШЕНО] |
| AR-21 | Восстановление доступа: при подключении нового устройства через QR админа — явная развилка одним тапом: «старое со мной / в ремонте → оставить сессию» \| «утеряно → завершить сессию». Никакого угадывания. | [РЕШЕНО] |
| AR-22 | Смена номера — явный шаг с ре-верификацией звонком на новый номер; автоопределение по симке запрещено. | [РЕШЕНО] |

## Отзыв прав и офлайн

| № | Решение | Статус |
|---|---|---|
| AR-23 | Отзыв прав — мгновенный, event-driven cascade: открытая страница закрывается сразу (push-канал WS/SSE — именованный контракт, не спроектирован); аккаунт не удаляется (остаётся гражданином, кроме глобального бана). | [РЕШЕНО]+[узел: контракт канала] |
| AR-24 | Регистрация и подключение к школе — online-only; офлайн покрывает локальную работу (записи сразу в локальную БД) и восстановление сессии. | [РЕШЕНО] |
| AR-25 | Локальные данные Tauri: шифрование at rest; ключ ре-выдаётся сервером при каждом коннекте, живёт N дней [дефолт 7]; отзыв → приложение стирает СВОЙ каталог (online — по event, offline — при первом синке); вечный офлайн → ключ протухает, база нечитаема. Удаление чужих файлов с диска пользователя — запрещено (траст/юридика/антивирусы). | [РЕШЕНО] |
| AR-26 | Файлы, скачанные пользователем на диск, — за периметром, это признаётся честно; контроль — разрешение «может скачивать» per-документ; «только просмотр» — best-effort флаг вьюера, не гарантия. | [РЕШЕНО] |
| AR-27 | Гонка «отзыв × офлайн-правки»: fail-closed — синк с отозванного аккаунта отклоняется целиком, данные школы не меняются, легитимные правки админ вносит вручную. Почему: частичный приём «до таймстампа» открывает подделку клиентских таймстампов. | [РЕШЕНО для v1] |

## Ресурсы, владение, роли

| № | Решение | Статус |
|---|---|---|
| AR-28 | Подписки/сервисы (entitlements): соло-школа покупает для себя → доступ её сотрудникам; в worknet покупает главная школа на всю сеть; не-главная школа не покупает без разрешения главной. База — kernel/entitlements (CONCEPT). | [РЕШЕНО] |
| AR-29 | Админ школы (CRM) и админ сети устройств (IT-директор/завхоз) — разные сущности в модели прав с этапа планирования; на старте роли совмещены одним человеком (это пакеты, AR-8). | [РЕШЕНО] |

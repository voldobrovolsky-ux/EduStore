# Сверка AUTH_FLOW/AR-реестра с кодом v1/v2 — противоречия и шаблоны

> Дата: 2026-07-08. Вход: `AUTH_FLOW.md` + `AR_REGISTER.md` (черновики стандартов,
> зафиксированы владельцем) × код v1 (корень репо) и экстракция `v2/`.
> Итог: доки внутренне согласованы; главный конфликт — с identity-фундаментом v1,
> который целиком ключевался на Флёр. Ниже — все расхождения с координатами.

## A. Противоречия «доки ↔ код» (что менять в переносимых кусках)

### A1. AR-1/AR-2 (EduStore самостоятелен) × весь identity-фундамент v1 — САМОЕ ГЛУБОКОЕ
Доки честно помечают «ADR-0005 пересмотреть», но следствие шире замены auth-модуля.
Ключ Флёра прошит в схему как **первичный ключ идентичности**:
- `User.id` = florus_user_id (`schema.prisma:98`, комментарий прямо в модели);
- `Teacher.id` = florus_user_id (FK → User, `schema.prisma:208`);
- `Membership.florusUserId` (`:159`), `Session.florusUserId` + флёровские
  access/refresh/id-токены как основные поля (`:170-188`);
- `docs/TENANCY.md`: «источник ключа тенанта — claim workspace_id логин-токена».

Для v2 по AR-1: нативный `User.id` (cuid), `florusUserId` — nullable unique
колонка-линк; в `Session` флёровские поля уходят в опциональную SSO-периферию;
`flor.service` перестаёт быть kernel-компонентом и становится интеграцией
(`domains/integrations/flor`), выпуск сессий — собственный. Переносимое ядро
auth при этом живёт: cookie httpOnly + серверная сессия + `@Public`/`@CurrentUser`
+ fail-closed dev-bypass не зависят от того, кто выпустил идентичность.
**TENANCY.md и ADR-0005 требуют редакции** — они противоречат AR-1 в текущем виде.

### A2. AR-4/AR-7 (телефон — ключ, merge по номеру) × User без телефона
`User` (schema:97-105): firstName/lastName/displayName/email? — **нет phone,
пола, ДР, @handle**. Merge по номеру (M4) невозможен без уникального
верифицированного `phone`. SMSAero-верификации в коде нет (честно помечено
слотом). Нужны: `phone @unique` (верифицированный), `handle @unique`
(citext-семантика, AR-5), пол/ДР, таблица резерв-имён, лог смен handle.

### A3. AR-8 (роль = пакет, роли совмещаемы) × одна роль на Membership
- `Membership`: одна строка `florusRole` + `subRole?`, `@@unique(user, workspace)`
  (schema:157-167) → **одна роль на школу, совмещение невозможно**;
- `Session.role` — роль зафиксирована на всю сессию (schema:177);
- `authz/catalog.ts`: ключ пакета = роль/суб-роль, `PermissionGuard` резолвит
  по одной роли.
Для AR-8 нужно: Membership ↔ N пакетов (join-таблица), резолв прав = **union
пакетов**, роль в сессии — не источник прав, а отображение. Механика
`ROLE_PACKAGES`/`syncAuthzCatalog`/`@RequirePermission` это выдерживает —
меняется резолвер, не паттерн.

### A4. AR-9 (QR не создаёт аккаунт) × pilot.service создаёт
`pilot.service.ts:144-150`: первый вход по инвайту **создаёт User + Membership
+ Session одним шагом** — прямое нарушение AR-9 (источник дублей идентичностей,
ровно то, что AR-9 запрещает). Шаблон пригоден (см. C1), но это место
переделывается: токен инвайта только привязывает membership к существующему
аккаунту; нет аккаунта → M1, затем привязка тем же токеном.

### A5. AR-10 (TTL 5 мин) × PilotInvite TTL 7 дней
`pilot.service.ts:15`: `INVITE_TTL_MS = 7 дней` против 5 минут в AR-10.
Остальное совпадает: одноразовость есть (`INVITE_USED`, :134), роль выбирается
до генерации (`PilotInvite.role`, schema:1181), статус invited→active виден
админу (:80). Расхождение только в TTL и в отсутствии деталей результата
(«подключился @handle, ФИО»).

### A6. AR-14/AR-18 (cookie 10 лет, хаб сессий, автозавершение 12 мес) × Session v1
- `SESSION_TTL_MS = 30 дней` скользящий (`flor.service.ts:23,238`) — v1 строже
  дока: сессия умирает через 30 дней неактивности. Конфликт дефолтов
  (30 дней ↔ 12 мес + кука 10 лет) — решить один.
- `Session` не имеет полей хаба: нет названия устройства, типа
  (mobile/web/desktop), маркера личное/общее (AR-15), trusted (AR-17),
  lastActivityAt (для AR-18 нужен отдельно от expiresAt). `Session.name` — это
  ФИО человека, не устройства.
- Удобное совпадение: `Session.workspaceId` уже nullable — «личная сессия без
  организации» (AR-19) ложится на существующее поле.

### A7. AR-14/15 («сеть устройств пользователя») × Device v1 (киоск школы)
`Device` (schema:193-204) — **устройство школы** (workspaceId, deviceToken,
киоск). AR-14/15 описывают **устройства пользователя** (хаб владельца). Это две
разные сущности; вторая в коде отсутствует. Не переименовывать одну в другую:
школьный киоск остаётся (общее устройство по AR-15), user-device добавляется.

### A8. AR-23 (мгновенный отзыв, push WS/SSE) × отсутствие realtime-канала
WS/SSE в коде нет нигде (доки честно держат [узел]). Событийная часть каскада
готова: outbox/inbox/`continuation()`+depth-guard. Образец «убить сессии по
событию» уже есть — backchannel-logout в `flor.service` (kill сессий по
sub/sid). Не хватает только транспорта до открытой страницы.

### A9. Membership FSM (активна/отозвана) × Membership без статуса
FSM в AUTH_FLOW §6 требует состояний, а `Membership` (schema:157-167) не имеет
`status`/`revokedAt` — отзыв в v1 не смоделирован вовсе (удаление строки =
потеря истории; статус-экран «доступ отозван + причина» строить не из чего).
Добавить status + revokedAt + причину; событие `membership.revoked` → каскад A8.

### A10. AR-24/25 (Tauri+SQLite, шифрование, wipe) × PWA-офлайн v1
Desktop-клиента в v1 нет; офлайн v1 — это `sw.js` (network-first кэш PWA).
Это **другая офлайн-модель**, и она не удовлетворяет AR-25 (нет шифрования
at rest, нет ключа с TTL, нет wipe по отзыву). Продуктовая развилка, которую
доки не проговаривают: судьба PWA-офлайна на web/mobile при появлении Tauri —
оставить web тонким (кэш только статики), офлайн-работа = только desktop?
Рекомендация: да, иначе SYNC.md придётся писать для двух клиентов сразу.

### A11. AR-28 (worknet-закупки) × Entitlement только per-workspace
- `Entitlement.workspaceId` — единственный скоуп (schema:557-570);
- `Worknet` (schema:122-133) **не имеет «главной школы»** — понятие из AR-28/AR-19
  не представлено; `EntitlementInterceptor.isActive` смотрит только тенанта.
Нужны: `Worknet.mainWorkspaceId`, скоуп у entitlement (workspace|worknet),
резолв «моя школа в сети N → активен ли worknet-грант», разрешение главной
школы на закупку не-главной.

### A12. AR-29 (админ сети устройств) × каталог пакетов v1
В `catalog.ts` (ROLE_PACKAGES:75-81) нет пакета device-admin; более того, v1
намеренно выносил admin/owner из RP-каталога («ведёт панель Флёра» —
TENANCY.md) — это следствие вытесненного ADR-0005 и с AR-1 больше не работает:
свои админ-пакеты (CRM-админ, IT-админ) должны жить в собственном каталоге.
Механика позволяет добавить каждый одной записью.

## B. Внутренние узлы самих доков (не блокируют, но решить)

1. **AR-9 × AR-10, гонка TTL**: QR ведёт нового пользователя в M1 (регистрация
   с верификацией звонком), «затем привязка тем же токеном» — но токен живёт
   5 минут. Регистрация+звонок легко дольше. Варианты: TTL считать до первого
   скана (скан = резервация токена), либо обмен токена на долгоживущую
   «заявку на привязку» при входе в M1.
2. **FSM устройства S4 × 1..N школ (AR-3)**: «отзыв прав (event) → S4 доступ
   отозван» на уровне УСТРОЙСТВА. Но отзыв — это membership одной школы;
   у сотрудника 1..N школ. S4 корректен, только если отозвана единственная/
   активная membership; иначе переход = смена активного workspace, не S4.
   В FSM не хватает этого ветвления.
3. **AR-16 (замок на ЛЮБОМ устройстве) × web**: на web нет secure storage —
   PIN-замок браузерной вкладки декларативен. Пометить web как best-effort
   (как уже сделано для скриншотов в AR-11) либо исключить web из дефолта.

## C. Шаблоны из существующего кода под маршруты (готовое к переиспользованию)

| Маршрут/AR | Шаблон | Что берём | Что чинить |
|---|---|---|---|
| **M2 (QR-инвайт)** | `modules/pilot/pilot.service.ts` (v1; в v2 не переносился — вернуть как шаблон) | одноразовость (`INVITE_USED`), TTL, роль-до-генерации, статус видимый админу, «сессия той же формы» | A4 (не создавать аккаунт), A5 (TTL 5 мин), результат с @handle |

| **M6 (восстановление)** | там же, ветка `purpose=kiosk` (подтверждение с телефона) | паттерн «новое устройство подтверждается уже-авторизованным» | развилка AR-21 одним тапом; видимость по AR-19 |
| **M5 (сессия)** | `v2/kernel/auth/flor.service.ts` | httpOnly cookie + серверная сессия + скользящий TTL (:236-238) | TTL-политика по A6; поля хаба сессий |

(journal/planning/teacher — там для auth ничего нет), а в выброшенном `pilot/`
и в перенесённых kernel/oidc-device — таблица выше это фиксирует.

## D. Что обновить в каноне v2 по итогам заморозки
1. `TENANCY.md` — источник тенанта: не claim Флёра, а собственная сессия
   (Флёр-claim — опциональный синк). §A1.
2. `adr/0005` — статус «вытеснен AR-1»: Флёр = опциональный SSO-коннектор;
   новый ADR-0006 «self-sovereign identity» со ссылкой на AR-реестр.
3. `v2/README.md` карта: `kernel/auth` → разделить на `kernel/session`
   (as-is) и `domains/integrations/flor` (concept).
4. Схема v2: User(+phone/handle/пол/ДР), Membership(+status, +пакеты N:M),
   Session(+поля хаба), UserDevice (новая), Worknet(+mainWorkspaceId),
   Entitlement(+scope). PilotInvite не переносится — заменяется
   InviteToken по AR-10.
